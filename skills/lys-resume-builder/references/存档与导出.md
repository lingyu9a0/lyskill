# 案例目录、存档与导出

## 一个用户，一个长期目录

默认案例根目录为 `~/Documents/resume-cases`。首次 Intake 收到材料后，以当日日期和用户代号建立：

```text
resume-cases/
└── <日期>-<用户代号>/
    ├── profile.md
    ├── experience-master.md
    ├── evidence.md
    ├── job-signals.md
    ├── jds/
    │   ├── <JD编号>-<公司>-<岗位>.md
    │   └── <JD编号>-match-v1.md
    ├── resumes/
    └── changelog.md
```

脚本还会建立隐藏的 `.records/` 与 `.labels/` 保存机器记录，并在需要导出文件时建立 `exports/`。这些目录不替代用户可读的 Markdown 资产。

不同用户必须使用不同案例目录。已有案例目录时直接继续，不再新建同名案例或重新访谈。代号必须经过安全化处理；为空、只有符号或可能与他人混淆时先确认。

## 稳定底层资产

- `profile.md`：称呼、教育背景、毕业时间、求职阶段、目标方向和已确认的基本信息；
- `experience-master.md`：完整保存真实经历，不受一页限制；
- `evidence.md`：保存原话、材料位置、状态、数字口径、结果和纠错关系；
- `job-signals.md`：保存证据能够支持的岗位任务、支持范围和证据 ID；
- `changelog.md`：记录素材母版更新、JD 匹配和每个简历分支的版本变化。

不创建 `resume-master.md`。真正的母版是 `experience-master.md`、`evidence.md` 和 `job-signals.md`。旧案例中已经存在的 `resume-master.md` 作为历史文件保留，不删除、不覆盖，也不再作为后续生成依据。

新增事实、纠错或新作品先更新底层资产，再生成或修改岗位分支。不能只改某份投递简历而让母版失去事实来源。

## JD 与投递版本

每个真实 JD 必须有唯一 `jd_id`、公司、岗位和原文，保存到：

```text
jds/<JD编号>-<公司>-<岗位>.md
```

同一 `jd_id` 的原文已经保存后不得静默替换。JD 内容发生实质变化时使用新的编号，或明确建立新的 JD 记录。

投递版保存到：

```text
resumes/<公司>-<岗位>-<JD编号>-v1.md
resumes/<公司>-<岗位>-<JD编号>-v2.md
```

两个岗位名称相同但 JD 不同，仍建立不同分支。同一分支已有版本时，新版本必须指定父版本并记录修改原因；不能只写“优化了一下”。

## 机器输入

以下仅为字段示意，示例不能写成用户事实。

素材母版至少包含：`kind=master`、`profile`、`evidence`、`job_signals`、结构化 `experiences`、完整经历、`workflow_state`、`change_reason` 和 `changes`。每段经历分别保存 `source_type`、`execution_status`、`start_date`、`end_date` 和 `duration`。

匹配记录使用 `kind=match`，另需 `company`、`target`、`jd_id`、`jd_text`、`task_clusters` 和 `match_matrix`。它保存任务建模、直接或代理证据、证据等级、缺口、回补结果、硬门槛和风险，不创建简历文件。

投递版使用 `kind=tailored`，必须引用最新 `source_master_version` 和已经保存的 `source_match_version`，并记录已经重新读取两者。同一 JD 的 v2 及以后还需 `parent_version`。

`task_clusters` 把零散 JD 归并成核心任务对象、动作、交付物或结果和期望证据。`match_matrix` 再记录每组候选证据所属任务簇、经历 ID、证据 ID、匹配状态、A—E 证据等级、岗位相关性、个人贡献清晰度、结果或交付物强度、是否入选、处理动作和回补状态。每个任务簇最多优先选择两组证据；E 级和未解决证据不进入投递版。

匹配记录必须保存 `allowed_evidence_ids` 和 `experience_order`。前者等于所有入选匹配行证据 ID 的并集，是该版本唯一可用的证据白名单；后者按对当前 JD 的证明力排列入选经历。投递版必须逐项复用这两个字段，不能重新选材或恢复已排除内容。

`jd-match` 与 `resume` 完全分离。匹配状态、缺口、风险和是否弱匹配只存在于前者。简历文件名和正文不带“弱匹配草稿”等诊断标签。

## 命令

首次建立案例目录：

```bash
python3 scripts/resume.py --base /absolute/resume-cases init-case --alias '用户代号'
```

保存母版或投递版：

```bash
python3 scripts/resume.py --case /absolute/resume-cases/2026-09-16-用户代号 save --payload /absolute/payload.json
```

查看、比较、恢复和导出：

```bash
python3 scripts/resume.py --case /absolute/case list
python3 scripts/resume.py --case /absolute/case compare --old old_id --new new_id
python3 scripts/resume.py --case /absolute/case rollback --id old_id
python3 scripts/resume.py --case /absolute/case export --id version_id --format docx
```

每次保存后读回机器记录和用户可读文件，并回显案例目录、版本名、父版本与实际路径。测试必须使用临时目录，不能写入真实案例。

## 导出

导出支持 HTML、DOCX、PDF，每次生成新路径，不覆盖旧文件。尚有事实占位符或未确认内容的草稿文件名明确含“草稿”；岗位匹配较弱本身不触发草稿命名。母版不作为投递文件导出。

DOCX 和 PDF 生成后必须回读文字；能够渲染时再检查中文、换行、溢出和分页。依赖缺失时如实降级，不声称已经生成目标格式，也不宣称所有 ATS 都兼容。
